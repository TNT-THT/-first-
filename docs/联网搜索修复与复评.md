## 1. 评分口径（先讲清楚，避免数字游戏）

## 2. 修了什么（按影响排序）

### 2.1 查询层（`web/src/search/query.js`）

| 问题 | 修复 | 位置 |
|---|---|---|
| 一句话被当成 shell 命令（7/20 空查询） | 含中文的行一律按自然语言处理；shell 识别改为「工具名 + 参数/子命令/文件名」，并要求命令行不像提问（`fails`/`why`/`error` 等词出现即按自然语言） | `isCodeLine` / `looksLikeShellCommand` |
| 相关性硬门槛误杀短技术词 | 术语加权：`AI/Go/C/C++/JS/TS/R/5G` 等 1–2 字符技术词进入词表并权重 ×2 | `SHORT_TERMS` / `termWeight` |
| 英文词形变化命中不了 | 轻量词干：复数、`-ing`、`-ed` 变体同时入索引（`goroutines` ↔ `goroutine`） | `stemVariants` |
| `X 和 Y 的区别` 只命中一个实体就出局 | 打分而非硬删：单命中降权但不判死；来源首条若有词面交集则保留，交给排序 | `scoreResult` / `MIN_RELEVANCE` |
| 翻译只覆盖 30 个词、且丢失问题意图 | 术语表扩到约 120 条 CS / 工程概念 + 意图词映射，`红黑树是怎么保持平衡的` → `red-black tree maintain balance` | `TERM_GLOSSARY` / `INTENT_PATTERNS` |
| 中文提问里的英文技术片段被浪费 | 新增 `englishFragment`：`CUDA out of memory`、`segmentation fault` 直接作为英文源查询 | `englishFragment` |
| 寒暄/纯代码也联网 | 新增 `isSearchWorthwhile` / `isTrivialQuery`，返回 `skipped` 而不是 `error`，0 请求 | 同名导出 |
| 凭据正则漏招 | 新增：数据库连接串、`mysql -p…`、AWS `AKIA/ASIA`、JWT、Slack webhook、中文「密码是…」 | `SECRET_PATTERNS` |

跨语言查询的优先级被明确成三级：

```
完整翻译（术语表 + 意图，保留问题意图）
   ↓ 没有
英文技术片段（问题里已有的英文），仍没有
   ↓
维基 langlinks 条目名（一次请求 + 缓存 + 命中相关性校验）
   ↓ 都没有
英文源整体跳过（0 请求，卡片显示“已跳过”），绝不外发中文原句
```

### 2.2 来源适配（`providers.js`）

- **langlinks 校验相关性**：`generator=search` 的首条命中必须与查询有词面交集（覆盖率 ≥ 20%），否则视为“没有翻译”。修复前模拟出的“把 `Microsoft YaHei` 当作 segfault 查询发给 SO/HN”不再发生。
- **Stack Exchange 优先有答案的问题**：请求带 `accepted=True`，返回里保留 `score / answer_count / is_answered`。
- **Hacker News 标记 `titleOnly`**：story 没有 `story_text` 时，snippet 不再冒充正文；排序降权，快速模式直接排除，深入模式只有补到讨论摘录才保留。
- **正文补充可裁剪**：`enrichWithExtracts` 支持分别开关维基/SO/HN，两种模式复用同一套逻辑。

### 2.3 编排与排序（`index.js` / `context.js`）

- **两种模式都补正文**：快速补前 2 条、深入补前 5 条并读 HN 讨论；`prepareSearchEvidence` 只要拿到正文就用正文（修复前只在 smart 模式使用，导致快速模式补了也白补）。
- **从“轮流坐庄”改为“相关性排序 + 来源配额”**：`rankResults` 按 `相关性 × 来源权重 × 是否有正文` 排序，默认每源最多 2 条，第二轮才放宽。HN 标题权重 0.6 且另有 0.45 惩罚。
- **空结果语义更诚实**：候选全是被过滤的标题/无关项时，返回 `ok=false` 并说明“未达到资料门槛”，不再出现 `ok=true, results=[]`。
- **查询计划随结果返回**：`plan = { keyword, en, enSource, providers, pages }`，界面直接展示“英文源实际查询 + 来源（术语表/技术片段/langlinks）”。
- **引用弱关联提示**：`auditCitations` 在编号存在之外，检查回答句与被引资料是否有词面交集；没有共同词时标为“关联较弱，请打开来源核实”（仍不声称能证明事实蕴含）。
- **来源时间**：`资料日期` 改为 `来源时间`，避免把维基最后编辑时间读成发布时间。

### 2.4 调用链（`main.js`）

- **模型加载与检索并行**：检索开始前先启动 `ensureReady`，检索结束后再等待；检索最多 12 秒不再叠加在模型加载之前。加载进度在检索阶段结束后继续上报。
- **`skipped` 状态**：寒暄/纯代码/空白显示「本条无需联网检索（已跳过）」，不标红、不发请求。
- **资料卡新增**：英文源实际查询与来源、弱关联引用提示、快速模式“也会补正文”的说明。

### 2.5 配置（`config.js` / `config.json` / README）

```json
"maxPerProvider": 2,
"minRelevance": 0.28,
"quick": { "maxPages": 2 },
"smart": { "maxPages": 5 },
"maxContextChars": { "quick": 3200, "smart": 6000 },
"stackexchange": { "site": "stackoverflow", "acceptedOnly": true }
```

同时清掉了已删除功能的过期注释（`china-static`），并同步更新 README 的流程、来源表、参数范围与默认值。

### 3.5 隐私边界（新增拦截，全部实测）

新增会触发 fail-closed（整次不联网）的形态：

```
mysql -u root -pSuperSecret123 …
postgres://admin:hunter2@10.0.0.5:5432/prod

AKIAIOSFODNN7EXAMPLE
eyJhbGciOiJIUzI1NiJ9.eyJzdWIiOiIxMjM0NTY3ODkwIn0.abcdefgh
```

正常技术讨论不会被误判：

```

cookie 和 session 有什么区别
token 是什么，JWT 怎么用
```

### 3.6 延迟

- 修复前：检索（最多 12s）→ 模型加载（WebLLM 数秒到数十秒）串行。
- 修复后：检索与模型加载并行；检索本身仍是“搜索 → 补充正文”两轮，但两轮都受同一个 12s 总预算约束，超时保留已到手的摘要并标 `partial`。
- 代价：快速模式多 2 个正文请求（维基导言批量 + SO 答案批量），换来 350 字有效证据。

## 4. 仍然存在的边界（不掩盖）

| # | 边界 | 影响 | 为什么这次没做 |
|---|---|---|---|
| 1 | **仍不是通用网页搜索**：默认只有维基百科 / Stack Overflow / Hacker News | 新闻、版本、赛事、博客正文仍搜不到 | 浏览器直连、无 Key、无服务器的约束下没有可靠的通用索引；SearXNG/自定义接口是唯一出路 |
| 2 | **查询规划仍是规则**，没有 LLM 改写/充分性重试 | 复杂指代、多跳问题、口语化长句仍可能抽取偏差 | 本地 WebLLM 加载成本高；需要额外一次生成与更复杂的中止/降级逻辑。评分表中该项只给 6.0 |
| 3 | **相关性是词面的** | 同义改写、反讽、跨语言概念差异仍会漏 | 没有可用的语义向量/重排服务；当前用术语表 + 词干 + 多翻译变体缓解 |
| 4 | **没有真实 API 集成测试** | CORS/配额/响应格式变化仍只能在真实浏览器发现 | 沙箱只能访问 github/npm/pypi；已保留人工冒烟路径与 `plan` 可观测信息 |
| 5 | **正则无法完备覆盖凭据** | 任意格式的秘密仍可能漏过 | fail-closed 只能覆盖已知形态；长期方案是“只外发关键词白名单”或本地脱敏 |
| 6 | **HN 价值仍偏低** | story 讨论常常答非所问 | 已降权并排除纯标题；是否默认关闭 HN 是产品取舍 |

## 5. 回归保护与复现

### 5.1 自动化测试

```
npm test        → 537 passed / 0 failed
npm run build   → 成功（含 pack-site）
```

`test/web-search.test.js` 从 67 → 79 个用例，新增覆盖：

- 8 类“自然语言被当成 shell 命令”的问题，以及真实命令仍被移除；
- 短技术词（AI/Go）与英文词形（goroutines）命中；
- 排序、每源配额、标题条目降权；
- langlinks 无关命中拒绝、相关命中接受；
- 翻译优先级（完整翻译 → 片段 → 条目名）；
- 快速模式补取维基导言 / SO 答案，且不使用只有标题的 HN；
- 寒暄/纯代码 `skipped` 且 0 请求；
- 新增隐私形态拦截与正常技术讨论不误判；
- 引用弱关联审计；
- 查询计划返回、`accepted=True` 请求参数、只有标题的 HN 不占编号；
- 中文站的弱命中保底不会阻止英文站回退（`二分查找的时间复杂度` 最终用 `Binary search`）。

### 5.2 复现实验

与修复前使用同一套模块级实验（无需网络、无需安装依赖）：

## 6. 下一步（如果要继续往 9 分走）

1. **把 LLM 放进查询环**（当前 6.0 的那一项）：模型判断是否需要检索、生成 1–3 条检索式、看结果是否足够再决定是否换词重试。可在模型已加载时启用，未加载时沿用现有规则。
2. **接 SearXNG 作为默认进阶源**：一个可信的 JSON 搜索后端能直接把“覆盖与扩展 7.0”抬到 8+，并让相关性过滤退化为“信任搜索引擎排序 + 轻量重排”。
3. **真实 API 冒烟测试**：默认 `skip`，CI 手动触发，监控 CORS、配额与响应格式。
4. **语义重排**：在本地可用的前提下，用轻量向量或模型对前 20 条做一次重排，解决同义改写与多跳问题。

> 最后仍然要说清楚：**这次修复把“能做的部分”从不及格做到了良好，但没有、也不可能把三个公开 API 变成整个互联网。** 准确性提升来自“不再误杀、不再用标题充数、把答案而不是题干交给模型”；覆盖边界仍在，且应该继续在 UI 与文档里明说。
