## 0. 一页结论

**总评：作为工程实现是合格偏优的；作为「AI 联网搜索」是不合理的。核心问题不是代码质量，而是搜索链路里没有 AI——查询理解、来源取舍、证据提炼三件事全部由正则和硬编码规则完成。**

| 维度 | 得分 | 一句话判词 |
|---|---|---|
| **搜索内容准确度** | **4.6 / 10** | 查询构建 3、来源命中 4、证据信息量 5、证据保真 6、归因可信 6 |
| **方案合理度** | **6.2 / 10** | 架构与约束匹配 8、隐私安全 6、性能预算 6、可观测 8、可维护 7、**产品覆盖 3**、体验 5 |

三条最硬的实测发现：

1. **一组 20 条常见开发提问里，7 条（35%）根本不会联网**。`Python 列表和元组的区别`、`Git rebase 和 merge 的区别`、`http 和 https 的区别`、`docker 容器启动就退出` 等被 `isCodeLine()` 的 shell 命令正则整行删掉，最终 `query=''`，用户看到的是红色「联网资料检索失败（没有可安全外发的问题文本可用于检索）」。
   *位置：`query.js:56`（shell 正则）；实测样本见附录 A。*

2. **相关性过滤器会毙掉维基百科刚刚返回的正确条目**。`AI 对齐问题是什么`：中文维基返回了 `AI 对齐`，但过滤器要求 3 个双字词命中 2 个、且 2 字母 token（`AI`）被直接丢弃，只命中 `对齐` 一个 → 判为无关；若该条目没有英文 langlinks，整次检索最终 `ok=false`（`没有相关结果`）。
   *位置：`query.js:287 tokenize` / `query.js:304 filterRelevantResults`；实测召回 5/10。*

3. **默认「快速检索」送给模型的不是答案，是题干和标题**。红黑树问题实测资料块 748 字符：维基摘要 27 字（泛泛定义）、Stack Overflow 203 字符（**问题描述**，不是答案）、Hacker News 34 字符（**就是标题本身**，`parseHackerNews` 的 `story_text || comment_text || title` 决定）。解释「红黑树如何保持平衡」的有效内容为 **0 字符**。同一问题切到「深入检索」后变成 1,038 字符，维基导言 180 + SO 采纳答案 340，才真正能支撑回答。

一句话终审：**这是一套把「三个 CORS 友好的公开 API」包装成搜索产品的、防御完备的资料侧栏；它的失败不在边界诚实，而在把一个需要语义理解的环节交给了正则。**

## 1. 它到底是怎么跑的

### 1.1 数据流

```
用户消息
  │
  ├─ analyzeSearchInput()            敏感信息检查 → 去代码块/行内代码/URL/代码行
  │    └─ pickQueryLine()            多行打分选一行（疑问词+内容丰富度，客套行重罚）
  │    └─ pickSentence(max 120)      截断
  │
  ├─ searchKeywords()                去停用词 → 关键词串（最多 120 字符）
  │
  ├─ [仅中文] resolveEnQuery()       再发一次 zh.wikipedia generator=search，取首条命中的英文标题
  │
  ├─ planProviders()                 默认 wikipedia / stackexchange / hackernews（+可选 DDG/SearXNG/自定义）
  │    └─ 四个来源 Promise.allSettled 并发，单请求 8s、总 12s
  │         ├─ wikipedia   zh 站优先 → 英文回退；结果先过滤一次
  │         ├─ stackexchange  只收英文查询；无法翻译则整源 skip（0 请求）
  │         └─ hackernews     同上
  │
  ├─ filterRelevantResults()         逐来源再过滤一次（bigram/单词重叠门槛）
  ├─ interleaveByProvider()          多源轮流取，每源一条一轮 → 最多 5 条
  │
  ├─ [smart] enrichWithExtracts()    维基导言 / SO 采纳或高分答案 / HN 讨论，只处理前 3 条
  │
  ├─ prepareSearchEvidence()         拼资料块，2400（quick）/ 4800（smart）字符硬上限
  └─ withSearchContext()             拼到最后一条 user 消息前面，并附加系统级「不可信证据」守则
```

### 1.2 关键参数（`config.js` 默认值 / `web/public/config.json`）

| 参数 | 值 | 实际影响（实测） |
|---|---|---|
| `providers` | wikipedia, stackexchange, hackernews | 无通用网页索引；DDG 即时答案默认关 |
| `defaultOn` / `defaultMode` | `false` / `quick` | 默认不联网；联网时默认只拿摘要 |
| `maxResults` | 5 | 四源轮流取，HN 经常占 2 席 |
| `maxSnippetChars` | 240 | **quick 模式的真实瓶颈**，不是 2400 预算 |
| `timeoutMs` / `totalTimeoutMs` | 8s / 12s | 超时后保留部分结果并标 `partial`，不缓存 |
| `smart.maxPages` | 3 | 5 条结果里只有前 3 条会补正文 |
| `maxContextChars` | quick 2400 / smart 4800 | 实测 quick 只用 748–1,846（31%–77%），smart 1,038–4,646 |

### 1.3 一次提问实际发多少请求

| 场景 | 请求数 | 说明 |
|---|---|---|
| 英文查询 | 3 | en.wiki + SO + HN |
| 中文查询，langlinks 翻译成功 | 4–5 | zh.wiki 搜索 + zh.wiki langlinks + SO + HN（zh 站无结果时再加 en.wiki） |
| 中文查询，无翻译 | 2 | 仅 zh.wiki 两次；SO/HN 标 `skipped`（0 外发） |
| 中文问候「你好」 | 2 | 同样发 2 个请求，然后返回「没有相关结果」 |
| smart 模式 | +1 维基导言 +1 SO 答案 +≤3 HN item +≤3 reader | 最多约 9–12 个 |

## 2. 搜索内容准确度（4.6 / 10）

准确度拆成五个可检验的环节，逐项给证据。

> 阅读提示：**[实测]** 的「字符数」来自本节构造的 mock 响应（长度按真实 API 的典型形态设定），用于说明流水线行为与上限；而「SO 摘要是问题 body」「HN 摘要是标题」「quick 不取答案」这些结论由代码路径直接决定，不依赖具体响应。真实 API 的命中率属于附录 C 的未验证项。

### 2.1 查询构建：3 / 10

**(a) 35% 的常见提问被当成 shell 命令丢弃** **[实测]**

`isCodeLine()` 里这条正则把「以工具名开头」等同于「代码行」：

```js
// query.js:56
if (/^(?:[$#]\s*)?(?:curl|wget|http|httpie|ssh|scp|docker|kubectl|npm|npx|pnpm|yarn|pip(?:3)?|python(?:3)?|node|git|export|set)\b/i.test(t)) return true;
```

由于 `\b` 后不要求任何参数，`Python 列表和元组的区别`、`http 和 https 的区别`、`set 和 dict 的区别` 全部命中。20 条常见提问样本实测：

| 输入 | 结果 |
|---|---|
| `Python 列表和元组的区别` | **空查询** |
| `Git rebase 和 merge 的区别` | **空查询** |
| `Node.js 和 Deno 的区别` | **空查询** |
| `npm 和 yarn 怎么选` | **空查询** |
| `http 和 https 的区别` | **空查询** |
| `set 和 dict 的区别` | **空查询** |
| `docker 容器启动就退出` | **空查询** |
| `Java 的 GC 怎么调优` / `Rust 的借用检查是什么` / `Redis 持久化怎么选` … | 正常 |

空查询的后果不是「静默不搜」，而是走 `status:'error'` 分支，UI 文案为：
`联网资料检索失败（没有可安全外发的问题文本可用于检索），本条回答未使用资料` **[实测]**

这是典型的过度纠正：为了堵住 `curl ... Authorization: Bearer ...` 的泄露，把「以工具名开头的自然语言」一并判死。加一行「含 CJK 的行不按 shell 命令处理」即可回收绝大部分，不会削弱安全（真实命令里极少夹中文；而 `export KEY=...` 仍由赋值正则覆盖）。

**(b) 查询词里保留大量无检索价值的成分** **[实测]**

| 输入 | 实际关键词 |
|---|---|
| `装好了环境，一直报 segmentation fault，这是为什么？` | `装好了环境 一直报 segmentation fault 这` |
| `我的代码提交后 WA 了，题目是两数之和，怎么改` | `我的代码提交后 WA 了 题目是两数之和 怎么改` |
| `二分查找 时间复杂度` | `二分查找 时间复杂度` ✅ |

「装好了环境」「我的代码」「这」这类口语成分对 BM25/维基搜索是纯噪声；`ZH_STOPWORDS` 只覆盖了 30 来个疑问词，没有「我的/这段/一直/怎么改」这类口语壳。

**(c) 没有查询改写、没有变体、没有重试** **[代码]**

`runWebSearch` 全程不调用模型；查询只有一条，失败就是失败。对比一个合理方案应具备：抽取意图 → 生成 1–3 条检索式 → 看结果是否足够 → 不足则换词重试。这里是「一发定生死」。

### 2.2 跨语言路由：4 / 10

设计意图是好的（中文问题不硬塞给英文源），但两个环节都靠不可靠的假设：

**(a) 英文源的门禁 = 「维基有没有对应条目」** **[代码][实测]**

只要中文查询且需要英文源，就先发一次 `resolveEnQuery()`：在 zh.wikipedia 用 `generator=search` 取**第一条命中的英文标题**。拿不到就整体跳过 SO/HN。

实测 `装好了环境，一直报 segmentation fault，这是为什么？` 在无翻译时：SO、HN 状态 `skipped`，0 请求外发。**隐私上是正确的，召回上是致命的**——中文用户最需要 SO 的编程报错类问题，恰恰最不可能在维基有对应条目。

**(b) 翻译只给「条目名」，丢掉问题意图** **[实测]**

`红黑树是怎么保持平衡的` → langlinks → `Red–black tree` → SO/HN 收到的查询是标题 `Red–black tree`，不是 `how does red-black tree maintain balance`。用户问的是「怎么保持平衡」，SO 收到的是一个名词短语，于是返回的也只能是「关于红黑树的问题」，与「机制解释」错位。实测 SO 命中 `How does a red-black tree maintain balance?` 纯属运气（mock 里我让它命中）。

**(c) 首条命中不校验相关性，可能污染全部英文源** **[模拟]**

`resolveEnQuery` 拿 `generator=search` 的第一条命中就直接取英文标题，**没有任何「这条命中与查询是否相关」的检查**。模拟一个维基首条命中为 `微软雅黑` 的响应：

```
resolveEnQuery('装好了环境 一直报 segmentation fault 这') → "Microsoft YaHei"
```

真实场景中，中文查询串含大量口语噪声（见 2.1b），维基搜索按 OR 匹配返回跑题条目并不罕见。一旦发生，SO、HN、英文维基会同时用这个无关标题检索，而相关性过滤器又因为「翻译变体」放行——**整轮证据全错，但卡片显示三个来源都成功**。

### 2.3 来源内容形态：3 / 10

默认三源各自能提供什么，实测如下：

| 来源 | quick 模式实际内容 | 问题 |
|---|---|---|
| 维基百科 | 搜索命中片段（`srprop=snippet`），实测 24–180 字符 | 只是「含关键词的一句话」，不是条目导言；概念解释经常不完整 |
| Stack Overflow | **问题 body** 前 240 字符（`providers.js:232`） | 用户要「怎么修」，拿到的是「我的代码为什么坏」；答案只在 smart 模式才取 |
| Hacker News | **标题本身**（`providers.js:254` 回退链：`story_text` → `comment_text` → `title`） | Algolia story 命中大多没有 `story_text` → `snippet === title`，占一个编号、约 130 字符元数据，有效信息 ≈ 0 |

同一个「红黑树如何保持平衡」问题，两种模式的资料块实测：

| 模式 | 块长度 | 条目 | 有效解释内容 |
|---|---|---|---|
| quick | 748 / 2400（31%） | 4 | 维基 27 字泛定义 + SO 题干 203 字符 + HN 标题 34 + 维基 24 → **0 字解释机制** |
| smart | 1,038 / 4,800（22%） | 4 | 维基导言 180 + SO 采纳答案 340 + 同上两条 → **能回答** |

结论很清楚：**问题不在预算（2400/4800 都远没用满），在于 quick 模式取的东西本来就没信息量。** 把 quick 的 2400 加得再大也没用——瓶颈是 240 字符摘要。

### 2.4 相关性过滤：3 / 10

`filterRelevantResults` 用 bigram/单词重叠做**硬门槛**（3 个以上术语至少命中 2 个，且覆盖率 ≥ 20%），不做打分、不做排序。

**(a) 召回实测：5 / 10 条「同主题正确来源」被保留** **[实测]**

| 查询 | 正确来源召回 | 误收 |
|---|---|---|
| `C++ 的虚函数表是什么` | 1/2（英文 `Virtual method table` 无翻译时被拒） | 0/1 |
| `Go 的 goroutine 和线程有什么区别` | 1/2（`Goroutines vs threads` 被拒） | 0/1 |
| `AI 对齐问题是什么` | **0/2** | 0/1 |
| `红黑树是怎么保持平衡的` | 1/2（`Red–black tree` 无翻译时被拒） | **2/2**（`B树`、`Show HN: 红黑树可视化`） |
| `2024年诺贝尔物理学奖的获得者是谁` | 2/2 | 0/1 |

三种可复现的误杀机制：

1. **短技术词被丢弃**：`tokenize` 只收 `[a-z]{3,}` 与 `\d{2,}`。`AI`、`C`、`C++`、`Go`、`JS`、`TS`、`R`、`5G`、`C#` 全部不成为术语。`AI 对齐问题` 只剩 `对齐/齐问/问题` 三个 bigram，页面只含 `对齐` → 1/3 < 门槛 2 → 正确条目被毙。
2. **无词干化**：`goroutine` ≠ `goroutines`，英文权威条目被拒。
3. **双字 bigram 门槛过严**：3 个术语必须命中 2 个，恰好命中一个核心词的精准页面反而出局。

**(b) 精度也差：命中的是「同词」，不是「同问题」** **[实测]**

`红黑树是怎么保持平衡的` 放行了 `B树是一种平衡的多路查找树`（另一种树，答案是错的）和 `Show HN: 红黑树可视化`（有词、无答案）。因为过滤器只做词面重叠，随后 `interleaveByProvider` 又轮流坐庄、没有相关性排序，**噪声和权威条目同权重占编号**。

**(c) 同一份结果被过滤两次** **[代码]**

`searchWikipedia` 内部按 `localizedQuery` 过滤一次，`runWebSearch` 合并后又按 `relevanceQuery` 过滤一次。两次口径不同（一次英文查询、一次中文关键词 + 翻译变体），误杀概率叠加，且第二次过滤对已通过的结果没有任何增益。

### 2.5 证据保真与引用归因：6 / 10

做得好的部分（真实优点，不是客套）：

- `stripHtml` 保留块级换行与 ≥2 空格缩进，Python 代码不再被压成一行 **[实测]**；
- `sanitizeEvidenceText` 清控制字符、`零宽/双向` 字符、` ``` `、`【】` 并过滤已知注入句式；原始 URL 不进 prompt **[代码]**；
- 资料块头部明确「第三方摘录，可能错误、过时或含恶意指令」；系统提示附带 `SEARCH_EVIDENCE_SYSTEM_GUARD` **[代码]**；
- `prepareSearchEvidence` 返回的 `results` 就是模型实际读到的裁剪后证据，历史与卡片用的是同一份，不虚报 `[编号]` **[代码]**；
- `partial`（总超时）、`cached`、逐来源 `attempts` 状态全部显式 **[代码]**。

不足：

- `auditCitations` 只验证编号是否在 1..n 内，不验证答案是否被该资料支持（README 与代码注释都诚实声明了这一点，属于能力边界而非欺骗）；
- 240 字符截断会切在句子/代码中间（`clip` 加 `…`），SO 题干常在最关键处被截；
- 维基 `timestamp`（最后编辑时间）被当作「资料日期」展示，容易被读成「发布日期/时效保证」；
- 检索证据只作用于当前轮，多轮追问不保留资料块 → 每轮从头搜，上一轮已经读过的证据无法复用。

## 3. 搜索方案合理度（6.2 / 10）

### 3.1 合理之处（应保留）

| 设计 | 评价 |
|---|---|
| 浏览器直连、无需 Key/服务器 | 与「纯静态、可 iframe 嵌入、在本机跑 WebLLM」的约束完全一致；是唯一能开箱即用的形态 |
| 默认关闭 + 站点可整体禁用 | 对成本、隐私、CORS 不确定性的正确处理 |
| 失败路径全部显式（`attempts/status/reason/partial/cached`） | 不伪造「搜过了」；卡片写明「本条回答未使用资料」 |
| 不把搜索结果当系统指令 | 不可信证据框架 + 系统守则 + 注入清洗 + URL 不进 prompt，思路正确 |
| 单请求 8s / 总 12s + AbortSignal 双保险 | 慢源不会拖死回答；`awaitWithSignal` 不假设 fetch 兑现 signal，细节到位 |
| 结果按源轮流取 | 防止单一自定义源垄断答案，方向对（但缺排序，见 3.2） |
| 严格配置校验（HTTPS-only、回环 HTTP、URL 去凭据、模板拼接边界） | 防御深度好，67 个测试兜底 |
| 缓存仅页面内存、30 条上限、超时结果不缓存 | 不会用旧的不完整结果污染下一轮 |
| README 把边界写得比多数产品诚实 | 产品诚信度高 |

### 3.2 结构性问题

**(1) 「搜索」的关键决策里没有 AI —— 这是方案层面的根本不合理** **[代码]**

一个 LLM 产品做联网搜索，正常分工是：

```
问题 → 模型判断是否需要检索 → 模型写检索式（可多轮） → 检索
     → 模型判断证据是否足够 → 不足则换词再检 → 模型抽取与回答 → 引用校验
```

这里的分工是：

```
问题 → 正则判断（永远检索） → 正则写检索式（一条） → 检索
     → bigram 过滤 → 轮流拼装 → 塞进 prompt → 正则数编号
```

模型只在最后一步「读资料」时参与。查询改写、来源取舍、证据提炼、充分性判断——四个最需要语义理解的环节全部交给了 250 行规则。这也是 2.1–2.4 所有缺陷的共同根因：正则擅长拒绝，不擅长理解。

**(2) 每轮无条件检索，没有「值不值得搜」的判断** **[代码][实测]**

`shouldSearch()` = `prefs.enabled && searchAvailable(...)`（`main.js:2019`），与消息内容无关。后果：

- 问候「你好」→ 2 个请求 → 返回「没有相关结果」→ 用户看到**失败徽章**；
- 纯代码消息 → 0 请求，但显示「检索失败：没有可安全外发的问题文本」；
- 「谢谢」「继续」同样触发；
- 每轮检索串行发生在模型加载之前，最多 12s 直接叠加在首 token 延迟上（本可并行）。

**(3) 默认 quick 模式与「刷题助手」的使用场景错配** **[实测]**

产品定位是刷题/编程答疑，默认模式却不取答案、不取导言，只取摘要和题干。上面红黑树的实测已经说明：quick 也能「成功」，但有效信息为 0。真正有用的 smart 模式需要用户手动切换，且只补前 3 条。

**(4) 覆盖边界决定了它不是「联网搜索」** **[代码]**

默认 = 维基百科 + Stack Overflow + Hacker News。新闻、版本发布、赛事题解、博客正文、任意网页，全部不可达。DDG 即时答案不是网页索引且默认关闭；SearXNG/自定义接口是唯一接近「全网」的路径，但默认未配置、需要部署者自建并改 CSP。README 对此完全诚实（「这不是通用网页搜索」），**但功能名、UI 文案、用户预期仍然是「联网资料检索」**。这是产品命名与能力的错配，不是实现 bug。

**(5) 预算参数与产出脱节** **[实测]**

quick 2400 预算实测只用 748–1,846 字符；smart 4800 实测 1,038–4,646。上一轮把预算从 1600/3200 提到 2400/4800 是对的方向，但**真正的瓶颈是 `maxSnippetChars=240` 与「quick 不取正文」**。调大预算不会增加一个字的有效信息。

**(6) 无排序、无去重（近重复）、无来源权重** **[代码]**

`interleaveByProvider` 按轮次取，`B树` 与 `红黑树` 同权；没有 `score` 字段，没有把维基导言排在 HN 标题前的机制；近重复（同一文章不同 URL）只按 URL 精确去重。

### 3.3 方案合理度小结

| 维度 | 得分 | 说明 |
|---|---|---|
| 架构与约束匹配 | 8/10 | 无服务器/无 Key 约束下的最优形态之一 |

## 5. 如果要把它做成「AI 联网搜索」，合理的目标形态

不需要推翻现有工程（超时、预算、审计、注入防护都该留），只需把四个语义决策交还给模型，并保持「证据不可信」的边界。

```
                      ┌── 规则层（保留）──┐
用户消息 → 敏感信息 fail-closed → 去代码/URL → 候选问题文本
                      └───────────────────┘
                                ↓
             ┌── 模型层（新增，本地 WebLLM 一次生成）──┐
             │ 1. 是否需要联网？（否 → 不发请求，标「已跳过」）│
             │ 2. 输出 1–3 条检索式（中/英各一条，保留意图）   │
             │ 3. 选择来源（概念→维基；报错→SO；动态→SearXNG）│
             └────────────────────────────────────────┘
                                ↓
                 并发检索（保留 8s/12s 预算）
                                ↓
      模型判充分性：不足 → 换检索式再检一次（≤2 轮）
                                ↓
      证据提炼：每源只留「能回答问题的那一段」，带 [编号]
                                ↓
              回答 → 编号审计（保留现状）
```

成本与收益（按本仓库的本地 WebLLM）：

| 改动 | 额外成本 | 预期收益 |
|---|---|---|
| 模型判断「是否需要搜」 | 1 次短生成（~0.5–1s，可并行） | 去掉问候/代码/闲聊的无效请求与失败徽章 |
| 模型写检索式 | 同一次生成 | P0-4 意图丢失、2.1b 噪声一次性解决 |
| 充分性判断 + 二次检索 | 仅在证据不足时 +1 轮 | 2.4 的召回问题从「硬门槛」变成「换词再试」 |
| 证据提炼（抽答案句） | 可与回答生成合并 | quick 模式的「题干/标题」问题消失 |
| 若坚持零模型参与 | 至少修 P0-1/P0-2/P0-3 + P1-1 | 从 4.6 分到约 6 分，仍受「三个 API」天花板限制 |

**如果部署者愿意配 SearXNG**，优先级应高于上面所有模型层改动：一个可信的 JSON 搜索后端能把「覆盖 3 个站点」变成「覆盖全网」，`filterRelevantResults` 也可以退化为「信任搜索引擎排序 + 轻量重排」，一次性解决 2.3/2.4 的大部分问题。

## 6. 公道话

这套实现的**工程品德明显高于它的产品能力**，而且很多优点在同规模项目里并不常见：

- 失败不伪装：搜不到就明说「本条回答未使用资料」，不拿模型记忆冒充检索结果；
- 证据可审计：模型读到的字符与历史里保存的字符完全一致（`prepareSearchEvidence` 返回 `results` 这一设计尤其正确）；
- 边界诚实：README 直接写「不是通用网页搜索」「不需要 API Key 不是隐私承诺」；
- 防御有深度：HTTPS-only、回环例外、URL 去凭据、模板拼接边界、控制字符/双向字符清理、AbortSignal 双保险、超时结果不缓存；
- 测试密度：1,251 行、67 个用例覆盖配置夹取、超时、取消、缓存、解析容错、注入过滤。

问题不在「写得差」，而在**用 1,909 行工程代码去弥补「没有语义理解」这一根本缺口**：正则能保证「绝不泄露」，但保证不了「搜得准」；bigram 能挡住无关页面，但挡不住「同词不同问题」，也放不过「同义不同词」。当查询构建、来源取舍、证据提炼三件事都由规则决定时，投入越多，边际收益越低。

**所以我的判断是：**

- **搜索内容准确度 4.6/10**——在「概念定义」这一窄带内可用（维基片段 + 明确术语），在「编程报错」「时效信息」「中文用户的英文资料」三类主要场景上不合格，且存在 35% 直接空转的硬缺陷。
- **搜索方案合理度 6.2/10**——作为受约束的静态站内「资料侧栏」，架构选择合理、工程质量优秀；作为「AI 联网搜索」，缺少 AI 参与的四项核心决策，产品定位与实现能力错配，因此整体只能算「合理的妥协」，不能算「合理的搜索方案」。

**下一步最划算的三件事**（按投入产出排序）：

1. 修 P0-1（一行 CJK 守卫 + 7 条回归用例）——回收 35% 的空转，成本约 30 分钟；
2. 修 P0-2/P0-3（白名单 + 词干 + 命中校验 + 去掉重复过滤）——把「正确条目被毙」变成「正确条目被保留」，成本约半天；
3. 默认改 smart + quick 补 SO 答案 + HN 限 1 席——让「成功」的检索真的有内容，成本约半天。

做完这三件，准确度可到 ~6.5/10；再往上（LLM 在环 / SearXNG）就不是代码问题，而是产品与部署决策了。
